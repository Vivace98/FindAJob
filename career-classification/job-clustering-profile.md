# 岗位聚类与求职准备能力画像

## 目的

本 skill 不建立职业名称或行业的漂亮分类，而是建立**求职准备分类**：同类岗位应能共享大部分能力准备、项目证据和简历母本；不同类岗位意味着需要明显不同的准备路径。

`workflow` 只用于识别基本工作方向。最终聚类由以下问题决定：

> 这些岗位能否用一套实质相同的能力训练、作品集证据和简历经历来准备？

它不做岗位准入筛选、薪资判断、个人能力盘点、投递排序、简历撰写或联网检索。

## 输入与边界

- 对每条筛选笔记，沿着 `raw_note_path` 读取 Raw 原文及其结构化字段。Raw 是 JD 证据的唯一来源；Filter 的工作形态和 Career Development 结论是筛选背景，不是聚类标签。
- 不修改 `Raw` 或 `Filter` 下的文件，也不重新纳入筛选阶段拒绝的岗位。

## 证据与能力提取

每个岗位的能力画像固定包含三个可见类别，类别内按能力在 JD 中**首次出现的顺序**排列：

1. `硬性能力`：工具、方法、分析或专业交付能力。
2. `软性能力`：沟通、协作、逻辑、表达、推进等 JD 明示的工作方式。
3. `行业认知`：JD 明示或由职责最小限度推出的业务流程、指标、法规、标准或领域机制。

对每项能力保留：

- `JD原文`：直接引文，或清楚标示的职责原文；
- `Skill总结`：不高估复杂度、权责或资深度的最小概括；
- `聚类标签`：仅供比较的规范化标签；
- `来源类型`：`explicit` 或 `inferred_from_responsibility`。

不要因公司属于某行业就虚构行业能力，不要把 Python、SQL、Power BI 等工具名自动升格为建模或工程能力。相同工具用于统计分析与用于生产管道不是同一种准备需求。重复出现的同一能力可合并，但保留全部实质证据和首次出现顺序。

若某类别没有 JD 支持，写“JD中未识别到明确要求”，不得以常识补齐。

## 工作特征：只作校准，不直接决定类别

将复合职责拆成任务，标注其主导 workflow：

- `Business Analysis`：业务指标、诊断、洞察与建议；
- `Statistical / Scientific Analysis`：统计设计、推断、方法有效性与科学解释；
- `Quantitative Decision Modeling`：预测、模拟、估值、风险、优化或情景决策；
- `Data Engineering / Delivery`：采集、转换、数据质量、查询、报表或交付；
- `Operational Execution`：上架、调价、活动提报、日常维护等预定义运营执行。

每项任务等权，除非 JD 明示比重。可记录主导和次要 workflow；无需生成精确到小数的伪精确权重，也不要据 workflow 名称直接完成聚类。

对每个岗位用事实说明下列三个维度：

- `Analytical Depth`：Level 0–4，从固定维护到统计设计／高阶建模；
- `Engineering Intensity`：Level 0–4，从无代码到生产级平台／部署；
- `Domain Barrier`：Level 0–3，从通用业务背景到强监管或专业方法门槛。

每个等级必须包含定义、JD 证据与理由。三个维度相互独立；`Domain Barrier` 也不等于跨岗位的领域可迁移性。

## 聚类规则：能力复用优先

先形成 workflow 相近的候选组，再按能力准备相似性决定是否保留、合并或拆分。评估至少包括：

1. **专业能力核心**：是否共享实质相同或可直接迁移的硬技能与方法，而非只有 SQL/Python 关键词重叠。
2. **问题与产出**：是否都在做类似的问题诊断、统计推断、预测／模拟、数据交付或运营执行，并产出类似成果。
3. **项目证据复用**：同一类案例是否能证明大部分岗位，例如“业务指标诊断报告”“统计分析计划与结果解释”“预测/情景模型”。
4. **简历母本复用**：是否可共享大部分经历表述、项目 bullet 和技能段落；只需补少量行业扩展的岗位才可同类。
5. **领域扩展成本**：领域差异是否能通过有限的指标/法规学习解决；若要求完全不同的监管体系、方法栈或专业训练，应拆分。
6. **工作层级与工程强度**：如果一组岗位的准备会在“业务分析”与“数据交付/工程”之间发生实质偏移，应拆分，即使有相同工具。

不用输出或假装计算完整两两相似度矩阵。对于边界模糊岗位，在类别笔记中写明“暂归入”以及导致归类变化的缺失事实。

一个最终类别必须通过四项检验：能力核心、共同准备计划、项目证据复用和简历母本复用。任何一项不成立就拆分。类别数量不预设；通常为 3–5 类，但以当前池能支持的最小充分类别数为准。单例仅在其专业能力树明显独立时保留。

## 能力画像聚合

每个类别仍按 `硬性能力 / 软性能力 / 行业认知` 聚合。

- `CORE`：至少 70% 的该类岗位有直接证据；
- `COMMON`：40–69%；
- `EXTENSION`：低于 40%，但对个别岗位重要。

按 `CORE → COMMON → EXTENSION` 排列；同层先按覆盖率，再按各岗位中最早出现顺序。可在类别层显示代表性 JD 说法，但规范化标签不能取代市场原话。行业认知要区分“共同核心”和“岗位专属扩展”。

## 写入结构

```
1.岗位/Classes/
├── _Career_Classification.md
└── <序号_类别名>/
    ├── _Cluster_Profile.md
    └── <与 Filter 同名的岗位>.md
```

`_Career_Classification.md` 必须包含：输入范围、最终类别数及理由、岗位—类别映射、各类别可复用的准备逻辑、跨类别共同基础、类别边界和暂归入项。

每个 `_Cluster_Profile.md` 必须包含：

1. 类别定义（从准备复用而非行业命名）；
2. 纳入岗位及其 workflow / 三个工作特征；
3. 四项聚类验证（能力、准备、项目证据、简历母本）；
4. 三类能力画像及 CORE/COMMON/EXTENSION；
5. 一套共享准备底座；
6. 每个岗位的行业或方法扩展；
7. 与相邻类别的边界。

每个岗位派生文件必须以实际的 Filter 链接开始，并包含：分类归属、任务级 workflow、三个工作特征、三类能力画像、共享核心、岗位专属扩展、以及为什么它能共享该类准备路径。不得复制完整 JD，也不得修改 Filter 文件。

## 交付与验证

交付前检查：

- 全部合格 Filter 岗位恰好各有一个派生岗位文件；
- 所有派生文件均链接到正确的 Filter 源文件；
- 每条能力有 JD 证据，推断与原文清晰区分；
- 类别内能力满足共享准备而不是标题、行业或工具重叠；
- 每个类别给出明确的项目证据原型和简历母本复用逻辑；
- 所有岗位专属要求均留作扩展，未被聚合过程抹掉；
- `CORE / COMMON / EXTENSION` 按类别内岗位覆盖率而非主观重要性划分；
- 不修改 Raw/Filter，不生成空类别或重复岗位文件。
